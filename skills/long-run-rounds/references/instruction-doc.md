# 指示書の骨組み

本文側（制作）とレビュー側に一つずつ。どちらも同じ節立てにする。§0〜§5 は親が読み、§6 は worker が読む。
親が読む部分は短く、表と決まった文だけにする。親は §5 の依頼文を**書かれたとおりに**渡し、行を足さない。

## §0 親がしてよいこと／しないこと

- してよい：状況表示の実行、worker の起動と待機、返却の先頭行を読む、記録ファイルへの一行追記、lock の作成・削除、定期再開の作成・削除。
- しない：本文・report・原著を読む、正本・queue・照合表の編集、数学の判断、依頼文の書き換え、**ユーザーへの質問・判断待ち**。

## §1 経緯・方針・現在地

- **経緯**：これまでの失敗を「何が起きた → どの規則にした（§番号）」で一行ずつ。改訂のたびに足す。
  worker が毎回読むので、同じ失敗を繰り返さない根拠になる。
- **方針**：ユーザーの方針（自走、採否の既定、順序、自己完結、頁数の扱い、容量）。
- **現在地**：日時つきで、冊ごとの照合表の数、被覆の数、閉じるまでに残っていることを本文側・レビュー側に分けて。
  次の単位が何かが分かるように書く。
- **ループの規則**：止まってよい場合の一覧。

## §2 開始時（スレッドで最初の一回。同じスレッドに貼り直されたときも）

1. 定期再開を作る：自分の古いものを消してから、一件だけ作る。本文側とレビュー側で分をずらす
   （例：本文 `5,20,35,50`、レビュー `12,27,42,57`）。prompt は「指示書の §3 から続ける」。
2. 記録に `<時刻> <版>で開始・定期再開 <分> 作成` と一行。
3. 最初の worker を出す。

## §3 再開時・ループ

1. 状況表示を実行し、その出力だけを見る。
2. 直前の返却が記録されていなければ一行書く（worker 自身も書くので重複させない）。
3. **容量の段階を先に見る**：停止前・上限中は worker を出さず `容量<段階> WAIT FP=…` と書いて終える。
   節約なら重いモデルを出さず、次の冊を先取りする仕事を止める。
4. 返却に応じて次を決める表：

本文側の表（例）

| 直前の返却 | 次 |
|---|---|
| 開始直後・再開直後・CONTINUE | 通常依頼 |
| NEED_PROOF | lock が無ければ作り、証明依頼。終わったら lock を消す |
| PROOF_DONE／FAILED | 通常依頼（取込みは worker） |
| WAIT | 状況表示に「本文側の仕事」（返却未閉鎖・queue未登録・整理が未）が一つでもあれば、一度だけ却下して通常依頼。無ければ §4 |
| BLOCKED | 理由を記録して通常依頼（詰まった行を飛ばす）。三回続いたら §4 |
| ALL_DONE | 照合表が全冊閉鎖なら定期再開を消して完了報告。違えば却下して通常依頼 |

レビュー側の表（例）

| 直前の返却 | 次 |
|---|---|
| 開始直後・再開直後・確認の RETURNED | 選定依頼 |
| 選定 → ASSIGN_MATH／SCOPE／OUTPUT | 対応する確認依頼（case path を入れる） |
| 選定 → ASSIGN_DECISIVE | lock が無ければ重いモデルで独立確認。あれば別の範囲を選定 |
| WAIT | §4 |
| ALL_DONE | 全冊閉鎖と完了フラグがあれば終了。違えば却下して §4 |

5. worker は model・subagent_type・effort を状況表示の値で明示し、run_in_background は false。同時に一本。
6. 返却を受けたら 1 に戻る。最終回答を出さない。上限の知らせが返ったら `上限 解除<時刻>` と書いて終える（定期再開は消さない）。

## §4 待機・上限・記録の読み方

- WAIT：`<時刻> WAIT FP=<FINGERPRINT>` と書いて短く終える。定期再開で起きて FP が同じなら何も出さない。
- 記録の worker 行は自分の worker が書いたもの。正本の書込時刻が動いていても「別のセッション」と推測して止めない。
- 定期再開は期限（例：7日）の前に作り直す。
- 容量の推定は下限の目安で、上限の知らせが正しい。

## §5 worker への依頼文

決まった文を置く。どの依頼文にも次を入れる：

- 最初に読むもの：指示書の §1 と §6、状況表示の出力、記録の末尾、今の冊の plan と照合表。
- 単位の種類と優先順：受領 → 整理 → 見直し → 照合 → 補完 → 提出（本文側）。選定 → claim → 種類の決定（レビュー側）。
- ユーザーに聞かないこと。迷ったら §6 の規則で決めて記録する。BLOCKED は技術的な障害だけ。
- 予算：ツール呼出の回数と文脈の上限。節約の段階ではさらに小さく。停止前・上限中は何も変えず WAIT。
- 記録：引継ぎ・進捗・記録ファイルへの書き方（時刻は書く直前に取る）。
- 返却の形：`STATUS:`・`NEXT:`／`NOTE:` の2〜3行だけ。
- **WAIT の条件**：状況表示の「本文側の仕事」の欄がどれも空で、今の冊にできる仕事がなく、全部がレビュー返却待ちのときだけ。

## §6 worker 用の規則（本文側）

- **目標と完了**：冊ごとの plan の採用範囲が正本。完了は照合表が閉じたときだけ。
- **受領**：返却を読み、直し、queue の作者状態を進める。上限で切れた後は最初に片付け（build 確認、古い lock、未登録 packet、途中の単位）。
- **軽微な修復の記録**：重大0・中0 の返却を直したら、その場で `review_coverage.py record-repair --case <case> --severity minor` を実行する。重大・中は記録せず再確認に回す。
- **溜まった「確認後に変更」の整理**：冊ごとに一度。確認した版と今の差が軽微な修復だけなら記録、他の変更が混じれば残す。済んだら決まった一行を記録する（状況表示がそれで「済」にする）。整理が「未」の間は WAIT を返さない。
- **cursor**：閉じていない最初の冊。後ろの冊の補完を先にしない。今の冊が全部返却待ちのときだけ、次の冊の照合（読むだけ）を進めてよい（容量が余裕のときだけ）。
- **照合表**：原著の側から番号ごとに行を作る（節一つを一行にして OK にしない）。状態は TODO・MISSING・PARTIAL・OK・OUT。OK はその冊の PDF に定義・主張・証明まであるときだけ。
- **採否の規則**（ユーザーに聞かずに決める）：1 plan が明記して除外し後続も使わない → OUT。2 他の冊が名指しで持つ・前提がそこにある → その冊へ送り、送り先に TODO 行。3 それ以外は採る。迷ったら採る。理由を表と plan に書く。
- **自己完結の照合**：証明で使う結果がその位置より前で証明されているか。欠けは表に行を足して埋める。
- **補完**：読書順に前から。一まとまりごとに build。
- **提出と閉鎖**：再照合は重大・中を直したときだけ出す。冊を閉じる条件は、最新の再照合に重大・中が無く軽微は直した、被覆の未確認・確認後に変更・確認中が0、返却が全部閉じた、の三つ。
- **成果物の置き場所**：packet・case は決まったディレクトリに絶対 path で作る。

## §6 worker 用の規則（レビュー側）

- 選ぶ順：自分の claim で未返却 → 公開済み未claim（照合 packet が最優先）→ 被覆表の候補（前の冊から、安定したものだけ）→ 最終bundle。
- 本文側の整理が「未」の間は「確認後に変更」の候補を取らず、「未確認」だけを取る。
- case は決まったディレクトリの直下に作る。状況表示が置き場所違いを出していたら、最初に移す。
- 独立性：case には固定の対象・直接前提・許可資料・中立な問いだけを入れる。作者の評価や先行 report は入れない。
- 照合 case は、原著の番号ごとに本文を探し、自己完結の欠けと採否の判断も問う。
- 記録された軽微な修復を疑って出し直さない。
