# 長時間の無人ラウンド

長い教材・本の制作とレビューを、人が張り付かずに何時間・何日も回すための型。
中身の規則（採用範囲・完了判定・レビュー契約）は [reading-book](../reading-book/SKILL.md)・
[course-authoring](../course-authoring/SKILL.md) が持ち、このスキルは**回し方**を持つ。

## 三つの役

| 役 | 誰 | すること | しないこと |
|---|---|---|---|
| 指示役 | ユーザーと話すセッション | 方針を決め、指示書・貼付文・状況表示の道具を書き、ときどき様子を見て規則を直す | スレッドの代わりに worker を回すこと。本文を書くこと |
| 親 | 制作とレビューを回す軽いモデル。一つの親、または役割別の親 | 状況表示を見て、表どおりに worker を一つ出し、一行記録し、定期再開で起きる | 本文・report・原著を読むこと。数学の判断。ユーザーへの質問 |
| worker | 毎回新しい文脈 | 指示書の §1・§6 を読み、一単位をして、2〜3行で返す | 単位をまたいで続けること。親の判断を代わりにすること |

親を軽くし、重い読み書きは worker に閉じ込める。親が本文を読むと、待機のたびに文脈が膨らんで容量が尽きる。

カードの本（[book-harness](../book-harness/SKILL.md)）では、一つの親が `labo book next --role all` を使い、
制作・独立確認・修復を一周として進められる。独立確認では固定版を新しい文脈の担当へ渡す。
この構成の指示書は[カードの本のラウンド](../book-harness/references/rounds.md)に従う。
親は軽い調整役とし、worker の能力は作業の役割で指定する。
返却待ちはホストの完了通知に預ける。起床は通知欠落・受付期限に対する復旧用とし、状態の変化がない待機では
ガードや進行票の読取を繰り返さない。カードの固定ケースで全対象が所見なしなら
[機械受領](../book-harness/references/review-receipt.md)で記録し、表示された一件を次に回す。
導入試行では同じ規模の完了単位あたりの親・受領担当のモデル呼出、新規入力、キャッシュ入力、出力と
レビュー被覆を採る。ホストの利用枠は実測できる場合に別に記録する。

週枠に停止点を設ける運転では、待機中の確認は一つのローカル処理に委ねる。Codex の場合は
[wait_codex_worker.py](scripts/wait_codex_worker.py) で親と担当の既存の実測記録を読む。履歴が変わったときだけ
再読し、担当の返却・中断、承認要求の候補、停止点・週枠の切替、goal の停止を一行で返す。
同じ担当を待つ間はその処理を継続し、残量や状態が変化しない待機で親を起こして履歴や進行票を読ませたり、
運転ログを追記したりしない。承認要求の候補は一度だけ通知し、ホストの表示で確かめる。
週枠を照合するためのモデル呼出は設けず、配付直前は現在の実測値も照合する。閾値・停止時の扱いは運転指示書に置く。

## 親の実行モデルを確認する

親モデルを指定した運転では、初回・自動継続・手動再開の各ターンで、配付前に
ホストの実行記録を照合する。画面の選択値や前ターンの値は配付の根拠に使わない。
ローカル Codex では現在のシェルに渡るスレッド ID と実行中のターンを
[check_codex_parent.py](scripts/check_codex_parent.py) で結び付ける。指示書から親モデルの
正確な ID を渡し、ネイティブ goal が必須なら `--require-active-goal` も付ける。
`--` の後ろに受付等のコマンドを置くと、照合が通った場合だけ実行する。
別モデルまたは照合不能なら新規配付・受付を止め、再開条件を一度表示する。
停止時の goal や起床の扱いは、ユーザーが指定した範囲で指示書に定める。
ホストの配付ツールを直接呼ぶ運転でも、直前の照合を配付契約に含める。

## 手順

以下は本文側とレビュー側に親を置く構成の手順。既存の役割別運用や、両側を並行して進める場合に使う。

1. **方針を決める。** ユーザーに次を確かめ、指示書の §1 に書く：自走か（スレッドはユーザーに聞かず規則で決める）、
   採るか迷ったときの既定（採る／採らない）、冊の順序（前から閉じる等）、自己完結の要否、容量の扱い、指定がある場合の親モデルと照合失敗時の扱い。
   指示役が推奨を出してよいが、決めるのはユーザー。
2. **状況表示を用意する。** 親が見るのはこの出力だけ。[round_status.py](scripts/round_status.py) に
   プロジェクトの設定 JSON（冊・queue・記録・case の置き場所など。鍵は script の先頭）を渡して使い、
   プロジェクト側には `--config` を固定した短い包みだけを置く。必要な欄と FINGERPRINT の作り方は
   [状況表示の契約](references/status-contract.md)。容量は reading-book の
   [usage_window.py](../reading-book/scripts/usage_window.py)、レビュー被覆は
   [review_coverage.py](../reading-book/scripts/review_coverage.py) を呼ぶ。
3. **指示書を二つ書く**（本文側・レビュー側）。節の骨組み、親の表、worker への依頼文は
   [指示書の骨組み](references/instruction-doc.md)。
4. **貼付文を書く。** [貼付文の雛形](assets/paste-prompts.md) を埋める。貼付文は短く、
   指示書の path と「§0〜§5 だけ読み §2 から」を言うだけにし、規則は指示書に置く。
5. **見守る。** 様子を聞かれたら、または規則を変えた後に、次を見る：
   - 両スレッドの記録の最後の時刻。定期再開の間隔より長く空いていれば、WAIT が正当かを状況表示で確かめる。
   - 閉じる条件の数（未確認・確認後に変更・照合表の不足）が**減っているか**。減らない・増えるなら、
     規則どうしの食い違いで空回りしていないかを疑う（[失敗と規則](references/failure-patterns.md)）。
   - 成果物が決まった場所にあるか（case の置き場所違いは被覆に数えられない）。
   - 容量の段階と、窓の終わり。
6. **訂正する。** 規則を直すときは：
   - 指示書は**同じファイル名のまま**改訂し、見出しに改訂時刻、§1「経緯」に「失敗 → 規則」を一行足す。
     worker は単位ごとに §1・§6 を読み直すので、そこに置いた規則は次の単位から効く。
   - 親の手順（§3〜§5）を変えたら、**動いているスレッドに貼付文を貼り直す**。定期再開はスレッドごとのもので、
     新しいスレッドからは消せない。新しいスレッドで始めるなら、先に古いスレッドを止める（親が二人になる）。
   - 状況表示の道具に欄を足すときは、その欄を FINGERPRINT にも入れる（入れないと待機中の親が気づかない）。
   - 大きな方針の変更は、言葉で示してユーザーの同意を得てから。
7. **止める・再開する。** ユーザーの停止指示では定期再開を解除する。親モデルの照合失敗では配付を止め、
   §1 で決めた goal・起床の停止手順を使う。上限到達・WAIT・ALL_DONE 却下では定期再開を維持する。
   再開は貼付文を貼り、指定モデルがある運転では新しいターンで照合する。

## 既定の規則（指示書に必ず入れる）

- 親は WAIT・正当な ALL_DONE・容量の段階による待機・実際の上限・親モデル照合の停止条件・ユーザーの停止指示以外で止まらない。
  一周や build の終わりで最終回答を出さない。
- 「完了」は、冊ごとの採用範囲の照合表が閉じたときだけ。レビュー queue が空なことは完了ではない
  （reading-book の[完了判定](../reading-book/references/book-workflow.md#章講義の完了判定)）。
- 再確認は収束させる：軽微な所見だけなら直して記録し、出し直さない
  （[容量と出し直し](../reading-book/references/capacity-window.md#spend-less-per-result)）。
- 容量の段階（余裕・節約・停止前・上限中）で仕事を変える（同上）。
- worker には model・subagent_type・effort を明示し、run_in_background は false。重い証明は排他 lock で一本だけ。
